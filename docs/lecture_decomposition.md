## 🚀 Вступление: от монолита к микросервисам {#вступление}

### ⚠️ Парадокс микросервисной архитектуры

Одна из ключевых истин в архитектуре — это противоречие, которое озвучивает **Мартин Фаулер**, авторитет в области ПО:

> **"Почти никогда не начинайте новый проект с микросервисов"**

**Почему?** Потому что:

1. **🎯 YAGNI (You Aren't Gonna Need It)** — почему усложнять архитектуру, если система может оказаться небольшой или неудачной? Монолит позволяет быстро проверить идею бизнеса на практике.

2. **🔍 Границы сервисов неочевидны** — успех микросервисной архитектуры напрямую зависит от **правильности определения границ** между сервисами. На ранних этапах, когда доменная модель ещё не стабилизировалась, это сделать сложно. В монолите легче проводить рефакторинг и экспериментировать.

3. **⚙️ Управление распределённой системой сложнее** — микросервисная архитектура вносит комплексность:
   - 🌐 Сетевые задержки и асинхронность
   - 📊 Проблемы с консистентностью данных
   - 👥 Мониторинг множества независимых процессов
   - 🔐 Безопасность и аутентификация
   - 📡 Синхронизация и согласованность

### 🔄 Жизненный цикл архитектуры

**Рекомендуемый путь эволюции:**

```
🏭 Монолит (MVP)
   ↓ [Эксплорация границ сервисов]
   ↓ [Понимание доменов]
   ↓
🏭 Монолит + первые микросервисы (Strangler)
   ↓ [Отщипывание сервисов]
   ↓ [Проверка границ в боевых условиях]
   ↓
🏛️ Микросервисная архитектура
```

**Три стратегии эволюции:**

- **Strangler Pattern** — постепенно отщипывать микросервисы с краёв монолита, оставляя исходную функциональность работать параллельно. (Фаулер, 2004)
  
- **Жертвенная архитектура (Sacrificial Architecture)** — относиться к исходному монолиту как к прототипу, который будет заменён, но служит средством познания системы.
  
- **Полная переписка** — только если монолит стал абсолютной помехой (редкий случай, требует больших инвестиций).

## 🔧 Методология декомпозиции {#методология}

### 7️⃣ Семи-шаговый процесс декомпозиции

Декомпозиция системы на микросервисы — это **итеративный процесс**. Вот структурированный подход:

#### Шаг 1️⃣: Описание пользовательских сценариев

**Что делать:** Выявить все способы, которыми пользователи (и другие системы) взаимодействуют с приложением.

**Формат:** User Stories в стиле BDD (Behavior-Driven Development):

```gherkin
🎯 Как [роль/актор]
я хочу [действие]
чтобы [получить результат]
```

**Пример для интернет-магазина сэндвичей:**

```gherkin
🎯 Как клиент
я хочу поместить сэндвичи в корзину
чтобы оформить заказ

🎯 Как маркетолог
я хочу создать акцию "-20% по понедельникам"
чтобы увеличить продажи
```

#### Шаг 2️⃣: Определение системных операций

Каждый user story требует одну или несколько **системных операций** — действий, которые приложение выполняет в ответ на внешний запрос.

**Примеры системных операций:**
- `createOrder()` — создание ордера
- `acceptOrder()` — принятие ордера в кафе
- `dispatchOrder()` — отправка заказа курьером
- `applyPromotion()` — применение скидки

Системные операции описывают поведение в терминах **модели предметной области** (domain model).

#### Шаг 3️⃣: Построение доменной модели

**Модель предметной области** — это набор **инвариантов** (условий, которые всегда должны быть истинны) и **ограничений**, описанных в терминах бизнеса.

**Ключевые сущности для системы доставки сэндвичей:**

| Сущность | Назначение |
|----------|-----------|
| **Order** | Заказ с инструкциями по приготовлению |
| **Store** | Кафе сети с адресом и расписанием |
| **Promotion** | Национальная или локальная акция |
| **MenuItem** | Сэндвич с ценой и ингредиентами |
| **Driver** | Курьер, доставляющий заказ |
| **DeliveryZone** | Зона доставки с расстояниями |

**Инварианты (бизнес-правила):**
- "Заказ может быть создан только если сумма ≥ минимум"
- "Сэндвич доступен только если все ингредиенты в наличии"
- "Доставка возможна только в зоне доставки (≤ 5 км)"

#### Шаг 4️⃣: Построение сервисной модели

На основе доменной модели выявляются границы будущих микросервисов. Это делается путём разбиения на **агрегаты** (в терминах DDD) или **функциональные области**.

**Результат:** Список микросервисов и их ответственность.

**Примеры для сэндвич-сервиса:**

```
🛒 Order Service
   ├─ Управление заказами
   └─ Валидация и расчёт цены

🎁 Promotion Service
   ├─ Национальные акции
   └─ Локальные акции

🏪 Store Service
   ├─ Информация о кафе
   ├─ Расписание работы
   └─ Зоны доставки

📢 Notification Service
   ├─ Email уведомления
   └─ SMS уведомления

👤 Customer Service
   ├─ Профили клиентов
   └─ История заказов
```

#### Шаги 5️⃣-7️⃣: Тестирование и итерация

Построенная модель проверяется:

- ✅ Может ли **каждая системная операция** быть выполнена с помощью определённых сервисов?
- ✅ Есть ли **чрезмерные зависимости** между сервисами?
- ✅ Можно ли **упростить или перераспределить** границы?
- ✅ **Все ли роли** могут работать независимо?

Проводится несколько итераций, пока архитектура не станет логичной и практичной.

## 📐 Паттерны разбиения {#паттерны}

### Паттерн 1️⃣: Разбиение по бизнес-возможностям (Business Capability)

**🎯 Идея:** Каждый микросервис отвечает за одну функциональную область бизнеса.

**✅ Преимущества:**
- Команды могут развиваться независимо
- Границы сервисов стабильны (не меняются часто)
- Соответствие организационной структуре (Conway's Law)
- Легко добавлять новые фичи в один сервис

**❌ Недостатки:**
- Может привести к дублированию кода между сервисами
- Сложнее отследить транзакции, пересекающие несколько сервисов
- Возможна слабая связанность разных компонентов

**🏗️ Пример для торговли сэндвичами:**

```
📦 Order Management Service
   ├─ Создание ордеров
   ├─ Отмена ордеров
   └─ Управление статусами

🎁 Promotion Management Service
   ├─ Создание акций
   ├─ Расчёт скидок
   └─ Управление сроками

🏪 Store Management Service
   ├─ Информация о кафе
   ├─ Расписание
   └─ Управление курьерами

📊 Analytics Service
   ├─ Сбор метрик
   ├─ Отчёты по продажам
   └─ Аналитика поведения
```

### Паттерн 2️⃣: Разбиение по субдоменам (Domain-Driven Design)

**🎯 Идея:** Использовать типологию доменов из DDD — разделить систему на **Core Domain**, **Supporting Domain** и **Generic Domain**.

| Тип домена | Описание | Пример |
|-----------|---------|--------|
| **Core Domain** | ❤️ Конкурентное преимущество компании | Алгоритм оптимальной маршрутизации курьеров |
| **Supporting Domain** | 💚 Важные, но не уникальные функции | Система уведомлений, кэширование |
| **Generic Domain** | 💙 Стандартные функции, встречаются везде | Аутентификация, логирование |

**✅ Преимущества:**
- Выделение областей, требующих особого внимания
- Разные подходы к разработке для разных доменов
- Generic Domain можно закупить как SaaS (например, Auth0)
- Понимание инвестиционных приоритетов

**❌ Недостатки:**
- Требует глубокого понимания бизнеса
- Типология может не совпадать с организационной структурой
- Сложнее на ранних этапах

### Паттерн 3️⃣: Разбиение по жизненному циклу (Lifecycle)

**🎯 Идея:** Разделить функциональность по фазам работы основного объекта.

**🏗️ Пример для заказа:**

```
📝 Order Creation Service (фаза 1)
   ├─ Валидация
   ├─ Расчёт цены
   └─ Подтверждение

⏳ Order Fulfillment Service (фаза 2)
   ├─ Приготовление
   ├─ Упаковка
   └─ Выдача

🚗 Order Delivery Service (фаза 3)
   ├─ Доставка
   ├─ Отслеживание
   └─ Подтверждение получения
```

**✅ Преимущества:**
- Каждый сервис отвечает за одну фазу
- Слабые связи между сервисами (фазы строго упорядочены)
- Легко отследить прогресс

**❌ Недостатки:**
- Может быть сложно с параллельными процессами
- Требует чёткого определения границ фаз

## 🏛️ Domain-Driven Design и Bounded Contexts {#ddd}

### 🎯 Концепция Bounded Context

**Bounded Context** — это явная граница, внутри которой действует **одна единственная модель** предметной области. Вне этой границы наступает другой контекст со своей моделью.

**Зачем это нужно:**

- 🔤 Один и тот же термин может означать разное в разных контекстах
  - "Customer" для Sales = потенциальный доход
  - "Customer" для Support = источник проблем
  
- 💾 В одном контексте используется одна схема БД, в другом — своя
  
- 🚀 Каждый контекст может эволюционировать независимо
  
- 🤝 Команды могут работать параллельно без конфликтов

### 🗣️ Ubiquitous Language (Единый язык)

Это **единственный язык**, используемый разработчиками и экспертами бизнеса в рамках одного **Bounded Context**. Все термины имеют точные определения.

**🏗️ Пример для Context "Доставка":**

| Термин | Определение |
|--------|----------|
| **Route** | Оптимальный маршрут, рассчитанный по дорожной сети через ГЛОНАСС |
| **DeliveryWindow** | Интервал времени доставки, согласованный с клиентом |
| **Driver** | Конкретный курьер, пересекающий маршрут |
| **DeliveryZone** | Географическая область, в которой сеть доставляет заказы |

### 📊 Типология Bounded Contexts

Bounded Contexts классифицируют по их роли в системе:

| Тип | Описание | Пример |
|-----|---------|--------|
| **Core** | Конкурентное преимущество | Алгоритм торговли в системе акций |
| **Supporting** | Важные, но не уникальные | Система уведомлений, кэширование |
| **Generic** | Стандартные функции | Аутентификация, логирование, Email |

## 🗂️ C4 Model для документирования архитектуры {#c4}

### 📋 Обзор C4 Model

**C4 Model** — это иерархический подход к визуализации архитектуры системы, разработанный **Simon Brown**. Состоит из 4 уровней диаграмм (отсюда название C4):

| Уровень | Название | Что показать | Что НЕ показывать |
|---------|----------|-------------|-----------------|
| **C1** | System Context | Саму систему и всех внешних актеров | Детали внутренней архитектуры |
| **C2** | Container | Основные приложения/БД и их взаимодействие | Классы и методы |
| **C3** | Component | Компоненты одного контейнера | Внутреннюю реализацию |
| **C4** | Code | Классы, методы, переменные | Обычно не используется для архитектуры |

### 🌍 Уровень 1: System Context

**Что показать:** Саму систему как чёрный ящик и всех внешних актеров.

**Пример для сэндвич-сервиса:**

```
┌─────────────┐
│    👤      │
│   Users    │
└──────┬──────┘
       │
   ┌───▼────────────────────┐
   │  🛒 Sandwich Shop      │
   │    Ordering Platform   │
   └───┬────────┬──────────┬┘
       │        │          │
   ┌───▼──┐ ┌───▼──┐  ┌────▼────┐
   │🗺️ Яндекс│ │💳 Платёжный│  │📧 Email  │
   │Карты │ │Шлюз│  │Сервис  │
   └──────┘ └─────┘  └─────────┘
```

### 📦 Уровень 2: Container

**Что показать:** Основные компоненты/приложения/базы данных и их взаимодействие.

**Что НЕ показывать:** Классы и методы внутри одного сервиса.

### 🔧 Уровень 3: Component

**Что показать:** Внутренние компоненты одного контейнера, их ответственность и взаимодействие.

**Что НЕ показывать:** Детали реализации (методы, переменные).

### 💻 Уровень 4: Code

**Когда использовать:** Обычно не нужна для архитектурных диаграмм. Используется в диаграммах классов (UML).

## 💼 Практическое применение {#практическое}

### 📋 Шаблон 1: Microservices Canvas (LaunchAny)

Простой формат для быстрого описания сервиса:

```yaml
📦 Service Name: Order Service

👥 Service Dependencies:
  - Payment Service (обработка платежей)
  - Inventory Service (резервирование товара)
  - Notification Service (отправка уведомлений)

🔄 Queries and Commands:
  - GET /api/v1/orders/{id}          # Получить заказ
  - POST /api/v1/orders               # Создать заказ
  - PUT /api/v1/orders/{id}/cancel    # Отменить заказ

📡 Event Subscriptions:
  - payment.completed
  - inventory.reserved

📤 Events Published:
  - order.created
  - order.confirmed
  - order.cancelled
```

### 📊 Шаблон 2: Bounded Context Canvas (DDD)

Более структурированный формат для анализа доменов:

| Аспект | Описание |
|--------|---------|
| **Название** | Order Management |
| **Классификация** | Core Domain |
| **Возможности** | Создание, подтверждение, отслеживание заказов |
| **Описание** | Управление полным жизненным циклом заказа. Включает валидацию, расчёт цены, управление статусом. |
| **Бизнес-правила** | Заказ может быть создан только если сумма ≥ 500 руб. Заказ не может быть отменён после подтверждения платежа. |
| **Зависимости** | Payment (входящая), Inventory (входящая), Notification (исходящая) |
| **Ubiquitous Language** | Order, OrderItem, OrderStatus, Total, Payment, DeliveryAddress |

## 🎯 Заключение

**Декомпозиция микросервисов** — это не одноразовое упражнение, а **постоянный процесс эволюции архитектуры**.

### 🔑 Ключевые принципы:

1. ✅ **Начните с монолита** — используйте его как средство познания доменной модели
2. ✅ **Используйте DDD** — определите Bounded Contexts как естественные границы для сервисов
3. ✅ **Применяйте C4 Model** — визуализируйте архитектуру на разных уровнях абстракции
4. ✅ **Итерируйте** — готовьтесь к тому, что границы сервисов будут уточняться
5. ✅ **Документируйте** — используйте единый формат (Canvas) для описания каждого сервиса
6. ✅ **Сфокусируйтесь на контрактах** — определите API и события для взаимодействия

### ⚠️ Помните:

Правильная декомпозиция — это **искусство баланса** между:
- 🔹 Упрощением (малое количество больших сервисов)
- 🔹 Готовностью к масштабированию (нужные размеры сервисов)
- 🔹 Командной независимостью
- 🔹 Операционной сложностью

**"Это не вопрос выбора между монолитом и микросервисами. Это вопрос выбора правильного времени и места для каждого подхода."** (Мартин Фаулер)
