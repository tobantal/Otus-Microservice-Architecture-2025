# 📋 Домашнее задание 1: Декомпозиция микросервисов

## 🎯 Постановка задачи

**Кейс:** "I'll Have the BLT" — развивающаяся национальная сеть кафе-бистро для заказа сэндвичей.

**Задание:**
Выполнить разбиение архитектурной задачи на несколько микросервисов с учётом возможных изменений и масштабирования системы.

**Что требуется:**
1. ✅ Пользовательские сценарии (User Stories)
2. ✅ Схема взаимодействия микросервисов (C4 Model — контейнерная диаграмма)
3. ✅ Описание каждого микросервиса (назначение, ответственность, контракты)
4. ✅ Контракты взаимодействия между сервисами

---

## 📝 Краткий обзор решения

В решении предложена **микросервисная архитектура** с разбиением на 5 основных сервисов:

| Сервис | Тип | Зона ответственности |
|--------|-----|----------------------|
| 🛒 **Order Service** | Core | Управление заказами |
| 🎁 **Promotion Service** | Supporting | Акции и скидки |
| 🏪 **Store Service** | Supporting | Информация о кафе |
| 👤 **Customer Service** | Generic | Профили клиентов |
| 📢 **Notification Service** | Supporting | Уведомления |

**Взаимодействие:**
- **Синхронное (REST)** — для критичных операций
- **Асинхронное (RabbitMQ)** — для уведомлений и интеграции

## 1. 🎭 Пользовательские сценарии

### User Story 1️⃣: Заказ с самовывозом в кафе

```gherkin
🎯 Как клиент
я хочу заказать сэндвич онлайн и забрать его в кафе
чтобы не стоять в очереди и получить заказ в удобное время

📋 Дано:
  • Клиент авторизован в мобильном приложении
  • Клиент находится в радиусе обслуживания одного из кафе

🔄 Когда клиент:
  1. Открывает меню и видит доступные сэндвичи с локальными акциями
  2. Выбирает сэндвичи и добавляет их в корзину
  3. Выбирает ближайшее кафе и время самовывоза
  4. Выбирает способ оплаты (онлайн или в кафе)
  5. Подтверждает заказ

✅ Тогда:
  • Заказ сохраняется в системе
  • Кассиру кафе поступает уведомление с деталями
  • Клиент получает номер заказа и время готовности
  • Система показывает адрес кафе и маршрут (Яндекс.Карты)
  • На email приходит подтверждение с квитанцией (если оплачено онлайн)

⚙️ Системные операции:
  • createOrder() — создание заказа
  • validateOrder() — валидация (минимум, доступность)
  • calculatePrice() — расчёт цены с акциями
  • reserveInventory() — зарезервировать ингредиенты
  • publishOrderToStore() — отправить в кафе
```

### User Story 2️⃣: Доставка на дом

```gherkin
🎯 Как клиент в городе с доставкой
я хочу заказать сэндвич с доставкой домой
чтобы не выходить из дома

📋 Дано:
  • Клиент авторизован в приложении
  • Кафе предоставляет доставку в регионе клиента

🔄 Когда клиент:
  1. Выбирает "Доставка" вместо "Самовывоз"
  2. Вводит адрес доставки
  3. Проверяет, что адрес входит в зону доставки
  4. Видит время доставки и стоимость доставки
  5. Подтверждает и оплачивает заказ

✅ Тогда:
  • Заказ создаётся с типом "Доставка"
  • Курьеру отправляется задание с адресом и маршрутом
  • Клиент получает время доставки и телефон курьера
  • Уведомление о готовке отправляется в кафе
  • После готовки курьер забирает заказ и доставляет

⚙️ Системные операции:
  • validateDeliveryAddress() — проверить адрес в зоне
  • calculateDeliveryFee() — расчёт стоимости доставки
  • assignDriver() — назначить курьера
  • updateDeliveryStatus() — отслеживание статуса
```

### User Story 3️⃣: Создание акций (маркетолог и владелец кафе)

```gherkin
🎯 Как маркетолог сети
я хочу создать национальную акцию "Понедельник — все сэндвичи -20%"
чтобы увеличить продажи в начале недели

🎯 И как владелец кафе
я хочу создать локальную акцию "Вт-Чт: 3 сэндвича за цену 2"
чтобы привлечь клиентов в период затишья

⚙️ Системные операции:
  • createNationalPromotion() — создать акцию для всей сети
  • createLocalPromotion() — создать акцию для одного кафе
  • applyPromotion() — применить при расчёте цены
  • listActivePromotions() — показать активные акции в меню
```

## 2. 📊 Модель предметной области

### 🏗️ Ключевые сущности и правила

| Сущность | Атрибуты | Инварианты |
|----------|----------|-----------|
| **Order** | id, customerId, orderType, items, totalPrice, status, createdAt, readyAt, pickedUpAt | Сумма ≥ минимум. Статусы переходят только в определённом порядке. |
| **OrderItem** | id, sandwichId, quantity, price, instructions | quantity > 0. Цена = базовая цена с применёнными акциями. |
| **Sandwich** | id, name, basePrice, ingredients, available | Доступен только если все ингредиенты есть в наличии. |
| **Store** | id, name, address, coordinates, hasDelivery, hours, capacity | Принимает заказы только в рабочие часы. |
| **Promotion** | id, type, discountValue, applicableSandwiches, startDate, endDate, storeId | Национальная видна всем. Локальная только для одного кафе. |
| **Driver** | id, name, phone, storeId, location, available | Принимает заказы только если available=true. |
| **Inventory** | storeId, sandwichId, quantity, minThreshold | При quantity < minThreshold требуется пополнение. |

### 📏 Бизнес-правила

1. **Минимальная сумма заказа:** 500 рублей (может отличаться по кафе)
2. **Время приготовления:** 15–20 минут
3. **Срок доставки:** 30–45 минут в зоне доставки
4. **Зона доставки:** не более 5 км от кафе
5. **Максимум одновременных заказов:** зависит от capacity кафе
6. **Способы оплаты:** онлайн (Карта, СБП) или наличные в кафе/при доставке

## 4. 🔧 Описание микросервисов

### 1. 📦 Order Service (Сервис заказов)

**Назначение:** Управление полным жизненным циклом заказов

| Параметр | Значение |
|----------|----------|
| **Тип домена** | Core (ключевое конкурентное преимущество) |
| **Зона ответственности** | Создание, валидация, подтверждение, отслеживание заказов |
| **Зависимости** | Promotion (скидки), Store (доступность), Payment Gateway, Notification |
| **API операции** | GET /orders/{id}, POST /orders, PUT /orders/{id}/cancel, PUT /orders/{id}/confirm |
| **События** | Подписывается: payment.completed, promotion.created; Публикует: order.created, order.confirmed, order.ready, order.cancelled, order.completed |
| **База данных** | PostgreSQL (orders, order_items, status_history) |
| **Масштабирование** | Шардирование по storeId, горизонтальное масштабирование |

**Пример REST API контракта:**

```json

## 5. 🔗 Контракты взаимодействия между сервисами

### 5.1 Синхронное взаимодействие (REST API)

```
📦 Order Service → 🎁 Promotion Service
  GET /api/v1/promotions/validate
  Получить применимые акции при создании заказа

📦 Order Service → 🏪 Store Service
  GET /api/v1/stores/{storeId}
  Проверить доступность кафе и вместимость

📦 Order Service → 💳 Payment Gateway (внешний)
  POST /api/v1/payment/charge
  Обработать платёж (только при paymentMethod=ONLINE)

🏪 Store Service → 📍 Геолокация (Яндекс.Карты)
  GET /routing/getRoutes?from=...&to=...
  Расчёт маршрута и расстояния для доставки
```

### 5.2 Асинхронное взаимодействие (Event-Driven RabbitMQ)

```
📊 Поток событий:

📦 Order Service (Publisher)
         ↓
    🐇 RabbitMQ
    ├─ order.created
    ├─ order.confirmed
    ├─ order.ready

    ├─ Inventory Service         → Зарезервировать ингредиенты
    └─ Analytics Service         → Собрать метрики

## 6. 🚀 Масштабирование и отказоустойчивость

### 🔥 Горячие точки системы

| Компонент | Проблема | Решение |
|-----------|----------|---------|
| 📦 Order Service | Пиковая нагрузка (обед 12-14) | Горизонтальное масштабирование, Redis cache |
| 🏪 Store Service | Геолокационные запросы | PostGIS индекс GiST, кэширование |
| 🐇 Message Queue | Переполнение очереди | Увеличение количество consumers, sharding |
| 💾 Database | Много записей при пике | Батчинг вставок, шардирование по storeId |

### 🛡️ Обработка отказов

| Сценарий | Обработка |
|----------|-----------|
| 💳 Payment Gateway недоступен | Retry с экспоненциальной задержкой (3 попытки), показать ошибку |
| 🎁 Promotion Service упал | Использовать кэшированные акции из Redis (graceful degradation) |
| 🐇 RabbitMQ упал | Сохранить событие в БД, переправить позже (Outbox Pattern) |
| 🏪 Store Service упал | API Gateway возвращает 503, сообщение "Кафе временно недоступны" |

## 7. ✅ Тестирование архитектуры

### Сценарий 1: Happy Path (полный заказ)

```
1. Клиент создаёт заказ
   ↓
2. Order Service валидирует заказ
   ↓
3. Promotion Service применяет скидки
   ↓
4. Order Service сохраняет в БД
   ↓
5. Публикует event order.created
   ↓
6. Notification Service отправляет SMS: "Заказ принят. Готовка: 15 мин"
   ↓
7. Store Display выводит заказ на экран кафе
   ↓
8. Inventory Service резервирует ингредиенты
```

### Сценарий 2: Отмена заказа

```
1. Клиент отменяет заказ (статус PENDING)
   ↓
2. Order Service публикует order.cancelled
   ↓
3. Notification Service отправляет подтверждение
   ↓
4. Inventory Service освобождает ингредиенты
   ↓
5. Payment Service возвращает средства (если оплачено)
```

### Сценарий 3: Отказ Payment Gateway

```
1. Клиент пытается оплатить
   ↓
2. Payment Gateway returns 500
   ↓
3. Order Service retry'ит (exponential backoff)
   ↓
4. После 3 попыток показывает ошибку клиенту
   ↓
5. Заказ остаётся в статусе PENDING_PAYMENT
```

## 8. ⚠️ Предположения и граничные случаи

### 📌 Основные предположения

1. **Аутентификация:** JWT токены на API Gateway
2. **Сетевая надёжность:** Ненадёжная сеть (используем retry + async/await)
3. **Масштаб:** 5,000 одновременных пользователей, 200k заказов в день (peak)
4. **География:** Только города РФ с доставкой

### ⚠️ Граничные случаи

**Случай 1: Заказ в конце рабочего дня**
```
Если клиент в 23:55 оформляет заказ на 00:05,
а кафе закрывается в 00:00:
→ Отклонить заказ до подтверждения оплаты
```

**Случай 2: Все курьеры заняты**
```
Если все курьеры доставляют заказы:
→ Добавить заказ в очередь
→ Показать ожидаемое время доставки (+30 мин)
→ Отправить SMS при готовности курьера
```

**Случай 3: Потеря сигнала GPS**
```
Если курьер потеряет ГЛОНАСС сигнал:
→ Использовать последнее известное местоположение
→ Отправить SMS клиенту: "Связь прервана, мы вас найдём"
→ После восстановления — обновить данные
```

**Случай 4: Нехватка ингредиентов**
```
Если при подтверждении заказа нет ингредиентов:
→ Предложить альтернативный сэндвич
→ Отменить и вернуть средства
```

## 📈 Итоговая архитектура

### Компоненты системы:

✅ **5 микросервисов** с чёткой ответственностью  
✅ **REST API** для синхронного взаимодействия  
✅ **RabbitMQ Event Bus** для асинхронной коммуникации  
✅ **Redis Cache** для производительности  
✅ **PostgreSQL** как основное хранилище  
✅ **API Gateway** для аутентификации и маршрутизации  

### Преимущества решения:

✅ **Масштабируемость:** каждый сервис масштабируется независимо  
✅ **Отказоустойчивость:** graceful degradation, retry policies, circuit breaker  
✅ **Гибкость:** легко добавлять новые функции без переписки кода  
✅ **Независимость команд:** каждая может разрабатывать свой сервис  

### Риски и как их минимизировать:

⚠️ **Распределённая консистентность** → Eventual Consistency + Saga Pattern  
⚠️ **Сложность отладки** → Distributed Tracing (Jaeger) + Centralized Logging  
⚠️ **Сетевые задержки** → Кэширование + асинхронность  
⚠️ **Управление базами** → Database per service pattern + data replication
